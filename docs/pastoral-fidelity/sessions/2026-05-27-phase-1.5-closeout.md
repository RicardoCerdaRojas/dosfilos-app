## Retrospective

**Qué fue mejor que estimado.** El reuso de infraestructura de Phase 0/1 (SBLGNT/MorphHB providers, `lookupCrossReferences`, patrón de Gemini service, schema `wordStudies[]`) hizo que el código realmente nuevo fuera el orquestador + prompts + UI. El curated lexicon v1 con 50 entradas resultó suficiente para que el smoke de Juan 1:1 mostrara glosas de alta calidad (λόγος, θεός vienen del curated). El gate-by-sub-flag permitió shippear sin romper a usuarios de Phase 1.

**Qué tomó más tiempo.** No el código — el desbloqueo del smoke. Una cadena de causas no relacionadas con la implementación consumió varios turnos: (1) el allowlist server-side de `setUserFeatureFlags` rechazaba el flag nuevo; (2) el branch no estaba deployado (corría `main` viejo); (3) Vite servía bundle stale; (4) finalmente, el flag estaba activo en la cuenta equivocada. Cada capa parecía "el bug" hasta descartarla.

**Qué cambió del plan original.** Apareció un PR no planeado (#259, realtime profile). El plan asumía que un toggle de flag + reload bastaba, pero `useUserProfile` hacía fetch one-shot por sesión, dejando el flag stale hasta hard reload — UX inaceptable para "funcional". Migrarlo a suscripción realtime con `subscribeProfile` (infra ya existente) eliminó la fricción de raíz. También se agregó #260 (gate render test) como verificación automatizada del wiring flag→botón, cerrando el gap que antes requería inspección visual.

**Aprendizajes para fases futuras.** (1) Antes de pedir smoke al usuario, confirmar que el branch está mergeado + deployado + que el flag está en la cuenta correcta — verificar la trinidad deploy/flag/cuenta de un saque ahorra turnos de diagnóstico. (2) Los feature flags que gatean UI necesitan propagación realtime o el rollout per-user genera falsos negativos de "no funciona". `useUserProfile` ahora es realtime para todos los consumidores. (3) Un test de render del gate vale más que diez explicaciones — prueba el wiring sin depender del navegador del usuario.
